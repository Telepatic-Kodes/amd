  <action>
Add a new `linkedinEngagement` table to `convex/schema.ts` that caches LinkedIn post engagement snapshots. This table stores periodic snapshots of engagement metrics fetched from the LinkedIn API, respecting rate limits by caching rather than querying in real-time.

Table definition:
```
linkedinEngagement: defineTable({
  contentId: v.id("content"),
  linkedinPostUrn: v.string(),
  likes: v.number(),
  comments: v.number(),
  shares: v.number(),
  impressions: v.number(),
  clicks: v.optional(v.number()),
  engagement_rate: v.optional(v.number()),
  fetchedAt: v.number(),
  userId: v.optional(v.string()),
})
  .index("by_contentId", ["contentId"])
  .index("by_contentId_fetchedAt", ["contentId", "fetchedAt"])
  .index("by_fetchedAt", ["fetchedAt"])
  .index("by_userId", ["userId"])
```

Place it after the `linkedinPublishLog` table section, with a clear section comment header matching the existing style (`// ===========================================`).

Do NOT modify any existing tables. Only add the new table.

<task type="auto">
  <name>Task 2: Create analytics.ts with date-filtered queries, agent performance, and content pipeline metrics</name>
  <files>convex/analytics.ts</files>
  <action>
Create a new file `convex/analytics.ts` that exports analytics queries with date-range filtering. These queries replace/extend the basic `getAnalyticsOverview` in functions.ts for the enhanced analytics page.

Import pattern: use `query` from `./_generated/server`, `v` from `convex/values`, and `getUserId` from `./lib/auth`.

**Query 1: `getAnalyticsWithDateRange`** (covers AI-01 internal metrics + AI-02 time-series aggregation)
Args: `{ startDate: v.number(), endDate: v.number() }`
- Fetch all executions, filter by `timestamp` between startDate and endDate
- Fetch all tasks (filter by userId like existing pattern), filter by `createdAt` between dates
- Fetch all content (filter by userId), filter by `createdAt` between dates
- Calculate: totalExecutions, totalTokens (input+output+total), totalCost, avgDuration, successRate
- Group tasks by day (ISO date string key): { completed, failed, total } per day -- this is the AI-02 daily rollup
- Group executions by agentId: top 10 agents with count, success count, tokens
- Join agent names from agents table
- Include contentCreated count (total content pieces in date range) for AI-01
- Return: `{ overview: {..., contentCreated: number}, tasksByDay: {...}, topAgents: [...], recentExecutions: [...] }`
- This mirrors the shape of the existing `getAnalyticsOverview` but with date filtering

**Query 2: `getContentPerformance`** (covers AL-01 through AL-03)
Args: `{ startDate: v.number(), endDate: v.number(), sortBy: v.optional(v.union(v.literal("engagement"), v.literal("impressions"), v.literal("recent"))) }`
- Fetch content filtered by userId and date range (by createdAt)
- For each content piece with status "published", fetch its latest linkedinEngagement snapshot (query by_contentId_fetchedAt, take last 1)
- Return array of: `{ contentId, title, type, publishedAt, engagement: { likes, comments, shares, impressions, engagement_rate } | null }`
- Sort by the selected metric (default: engagement = likes+comments+shares)
- Limit to 50 results

**Query 3: `getAgentPerformanceSummary`** (covers AI-03 agent performance metrics)
Args: `{ startDate: v.number(), endDate: v.number() }`
- Fetch all executions in date range
- Group by agentId: calculate per agent: totalExecutions, successCount, failCount, successRate (successCount/totalExecutions*100), totalTokens, totalCost, avgDuration (total duration / totalExecutions)
- Join agent name and department from agents table
- Return sorted by totalExecutions desc, limit 20

**Query 4: `getContentPipelineMetrics`** (covers AI-04 content pipeline metrics)
Args: `{ startDate: v.number(), endDate: v.number() }`
- Fetch all content in date range (by createdAt), filtered by userId
- Calculate throughput: count of content pieces that reached "published" status in the date range
- Calculate status distribution: count of content in each status (draft, review, revision_needed, approved, scheduled, published, archived)
- Calculate avg time in pipeline: for published content, compute (publishedAt or updatedAt) - createdAt to estimate avg time from creation to publication
- Identify bottlenecks: find the status with the most content stuck (highest count in non-terminal statuses: draft, review, revision_needed)
- Return: `{ throughput: number, statusDistribution: Record<string, number>, avgTimeToPublish: number | null, bottleneck: { status: string, count: number } | null, totalContent: number }`

**Query 5: `getAnalyticsExportData`**
Args: `{ startDate: v.number(), endDate: v.number() }`
- Fetch executions, tasks, content (all filtered by date range and userId)
- Return flat arrays suitable for CSV conversion on the client:
  - executions: { timestamp, agentName, status, tokens, cost, duration }
  - tasks: { createdAt, title, type, priority, status, agentName }
  - content: { createdAt, title, type, status, likes, comments, shares, impressions }

All queries MUST call `getUserId(ctx)` at the start for auth. Follow the existing backward-compatible filtering pattern: `item.userId === userId || item.userId === undefined`.

Do NOT use `@convex-dev/aggregate` -- use simple in-memory aggregation over fetched records (the data volume is small enough for direct queries with `.collect()` and JS reduce/filter). This avoids adding a new dependency with limited production case studies (concern from STATE.md). The date-filtered queries with in-memory groupByDay logic satisfy AI-02 (time-series aggregation) without external dependencies.
