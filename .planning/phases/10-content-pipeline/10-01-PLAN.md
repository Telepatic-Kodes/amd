<objective>
Create the Convex backend queries and mutations that power the Content Pipeline Kanban board. These provide validated workflow transitions, status-grouped content queries, and scheduled content management.

Purpose: The existing `updateContentStatus` mutation in `functions.ts` accepts any status transition without validation. The Content Pipeline needs strict workflow rules (e.g., only drafts can be sent to review, only approved content can be scheduled). We create a dedicated `contentPipeline.ts` with validated mutations and optimized queries for the Kanban UI.

Key insight: The content table already has `by_status` and `by_scheduled` indexes in `schema.ts`, so queries will be efficient. The mutation validation prevents invalid state transitions that could confuse users.

Output: `convex/contentPipeline.ts` with queries and mutations ready for frontend Kanban consumption.

- Sorts by `scheduledFor` ascending (soonest first)
- For each item, returns: `_id`, `contentId`, `title`, `type`, `scheduledFor`, `createdAt`, `metadata`
- Returns array of scheduled items
- Used for the "Contenido Programado" scheduled content view

<task type="auto">
  <name>Task 2: Create validated workflow mutation functions</name>
  <files>convex/contentPipeline.ts</files>
  <action>
Add the following mutations to `convex/contentPipeline.ts`:

**Allowed transitions map (define as const at top of file):**
```typescript
const ALLOWED_TRANSITIONS: Record<string, string[]> = {
  draft: ["review"],
  review: ["approved", "revision_needed"],
  revision_needed: ["review"],
  approved: ["scheduled", "published"],
  scheduled: ["published", "approved"],  // Can un-schedule back to approved
  published: ["archived"],
  archived: ["draft"],  // Can reactivate archived content
};
```

**1. `moveContent` mutation (generic transition):**
- Args: `{ id: v.id("content"), toStatus: v.string() }`
- Fetches the content item, validates it exists
- Checks that the transition from current status to `toStatus` is in `ALLOWED_TRANSITIONS`
- If not allowed, throws descriptive error: `"Transicion no permitida: ${currentStatus} -> ${toStatus}"`
- Patches the content with new status + `updatedAt: Date.now()`
- If toStatus is "published", also sets `publishedAt: Date.now()`
- Logs to auditLog: `{ action: "content.status_changed", entityType: "content", entityId: contentId, performedBy: "user", changes: { from: currentStatus, to: toStatus }, timestamp: now }`
- Returns the updated content

**2. `moveContentToReview` mutation:**
- Args: `{ id: v.id("content") }`
- Validates content is "draft" or "revision_needed"
- Transitions to "review"
- Logs to auditLog

**3. `approveContent` mutation:**
- Args: `{ id: v.id("content"), approvedBy: v.optional(v.string()) }`
- Validates content is "review"
- Transitions to "approved"
- Sets `approvedBy` field if provided
- Logs to auditLog

**4. `rejectContent` mutation:**
- Args: `{ id: v.id("content") }`
- Validates content is "review"
- Transitions to "revision_needed"
- Logs to auditLog

**5. `scheduleContent` mutation:**
- Args: `{ id: v.id("content"), scheduledFor: v.number() }`
- Validates content is "approved"
- Validates `scheduledFor` is in the future (> Date.now())
- Transitions to "scheduled" and sets `scheduledFor` field
- Logs to auditLog

**6. `publishContent` mutation:**
- Args: `{ id: v.id("content"), publishedUrl: v.optional(v.string()) }`
- Validates content is "approved" or "scheduled"
- Transitions to "published", sets `publishedAt: Date.now()`
- If `publishedUrl` provided, sets it
- Logs to auditLog

Each mutation follows the pattern:
1. Fetch content by id, throw if not found
2. Validate current status allows the transition
3. Build update object with new status + timestamp
4. Patch content
5. Insert auditLog entry
6. Return updated content id

IMPORTANT: Use proper Convex arg validators (v.id, v.string, v.number, v.optional). Follow exact same import pattern as functions.ts.
