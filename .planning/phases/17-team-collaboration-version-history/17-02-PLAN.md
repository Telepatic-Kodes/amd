1. In convex/schema.ts, add `contentVersions` table AFTER the `content` table:
   ```typescript
   contentVersions: defineTable({
     contentId: v.id("content"),           // Reference to parent content
     version: v.number(),                   // Sequential version number (1, 2, 3...)
     // Snapshot of content at this version
     title: v.string(),
     body: v.string(),
     summary: v.optional(v.string()),
     metadata: v.optional(v.any()),         // Full metadata snapshot
     seo: v.optional(v.any()),              // Full SEO snapshot
     status: v.string(),                    // Content status at time of snapshot
     // Attribution
     editedBy: v.string(),                  // Clerk userId who made the change
     editedByName: v.optional(v.string()),  // Display name for UI
     changeType: v.union(
       v.literal("created"),
       v.literal("edited"),
       v.literal("status_change"),
       v.literal("rollback")
     ),
     changeSummary: v.optional(v.string()), // e.g. "Estado cambiado de borrador a revisión"
     createdAt: v.number(),
   })
     .index("by_contentId", ["contentId"])
     .index("by_contentId_version", ["contentId", "version"])
     .index("by_editedBy", ["editedBy"])
     .index("by_createdAt", ["createdAt"]),
   ```

2. Create convex/contentVersions.ts with:

   a) **Internal helper: createVersionSnapshot(ctx, contentId, changeType, changeSummary?)** — async function (NOT exported as API):
   - Get the current content doc by ID
   - Get the userId and user name from auth context (query users table for name)
   - Count existing versions for this contentId to determine next version number
   - Insert into contentVersions: full snapshot of title, body, summary, metadata, seo, status, editedBy, editedByName, changeType, changeSummary, createdAt
   - Return the new version doc ID

   b) **Query: listContentVersions({ contentId })** — export as query:
   - Args: contentId (v.id("content"))
   - Requires authentication (requireAuth)
   - Query contentVersions by contentId index, collect all
   - Sort by version descending (newest first)
   - Return array of version summaries: { _id, version, changeType, changeSummary, editedBy, editedByName, status, createdAt }
   - Limit to 50 versions max for performance

   c) **Query: getVersionDiff({ versionAId, versionBId })** — export as query:
   - Args: versionAId (v.id("contentVersions")), versionBId (v.id("contentVersions"))
   - Requires authentication
   - Fetch both version docs
   - Compute diff object:
     ```typescript
     {
       versionA: { version, title, body, summary, status, editedBy, editedByName, createdAt },
       versionB: { version, title, body, summary, status, editedBy, editedByName, createdAt },
       changes: {
         titleChanged: boolean,
         bodyChanged: boolean,
         summaryChanged: boolean,
         statusChanged: boolean,
         metadataChanged: boolean,
         seoChanged: boolean,
       }
     }
     ```
   - The actual text diffing will happen client-side (using a lightweight diff library). Backend just provides the two snapshots and flags which fields changed.

   d) **Mutation: rollbackToVersion({ contentId, versionId })** — export as mutation:
   - Args: contentId (v.id("content")), versionId (v.id("contentVersions"))
   - Requires authentication
   - Fetch the target version doc
   - Verify contentId matches version's contentId
   - Get userId and verify ownership (same pattern as updateContent)
   - Create a NEW version snapshot FIRST (type "rollback", summary "Revertido a versión {N}")
   - Then patch the content doc with title, body, summary, metadata, seo from the target version
   - Set content.updatedAt = Date.now()
   - Return the new version number

   e) **Internal helper: logContentAction(ctx, contentId, action, details?)** — for audit trail:
   - Insert into auditLog table (already exists in schema):
     - action: "content.{action}" (e.g., "content.created", "content.edited", "content.approved", "content.published", "content.rollback")
     - entityType: "content"
     - entityId: contentId string
     - performedBy: "user"
     - performerId: userId
     - changes: details object (optional)
     - timestamp: Date.now()

   All imports from "./lib/auth" (requireAuth, getUserId). All error messages in Spanish.

1. In convex/functions.ts, import createVersionSnapshot and logContentAction from "./contentVersions" as internal helpers. Since these are internal helpers (not API-exported), import them directly as functions.

   NOTE: Convex internal functions can be called via `ctx.runMutation(internal.contentVersions.createVersionSnapshot, args)` pattern, OR the helper functions can be extracted as plain async functions that accept ctx. Use the plain function approach: export the snapshot/audit logic as standalone async functions that receive ctx + args (not as Convex query/mutation wrappers). This avoids the internal function call overhead.

   Actually, the simplest pattern: Define `createVersionSnapshot` and `logContentAction` as plain exported async functions in contentVersions.ts (not Convex API endpoints). Then import and call them directly in functions.ts and contentPipeline.ts.

   Modifications to convex/functions.ts:

   a) **createContent handler**: After inserting the content doc, call:
   - `await createVersionSnapshot(ctx, newContentId, "created", "Contenido creado")`
   - `await logContentAction(ctx, contentId, "created")`

   b) **updateContent handler**: After patching the content doc, call:
   - `await createVersionSnapshot(ctx, args.id, "edited", "Contenido editado")`
   - `await logContentAction(ctx, args.id, "edited", { fields: Object.keys(updates).filter(k => k !== "updatedAt") })`

   c) **updateContentStatus handler**: After patching the content doc, call:
   - Build Spanish summary: "Estado cambiado de {oldStatus} a {newStatus}"
   - `await createVersionSnapshot(ctx, args.id, "status_change", summary)`
   - `await logContentAction(ctx, args.id, statusActionMap[args.status], { from: content.status, to: args.status })`
     Where statusActionMap maps: "review" → "sent_to_review", "approved" → "approved", "published" → "published", etc.

2. In convex/contentPipeline.ts, if there are mutations that change content (moveContent or similar):
   - Add the same version snapshot + audit log calls after any content modification.
   - If moveContent only calls updateContentStatus internally, no changes needed (the status mutation already handles it).

IMPORTANT:
- createVersionSnapshot and logContentAction are MUTATION-context functions (they write to DB). They can only be called from mutation handlers, not queries.
- The content ID passed to createVersionSnapshot must be the Convex document ID (v.id("content")), not the string contentId field.
- Performance: Version snapshots add one write per edit. This is acceptable — content edits are low-frequency human actions, not high-throughput operations.
