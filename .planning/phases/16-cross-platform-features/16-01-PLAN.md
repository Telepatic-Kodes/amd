  <action>
Create `ai-marketing-department/ai-marketing-department/lib/contentAdapters.ts` — a **shared pure TypeScript module** with NO Convex imports. This file is importable by both the Convex backend (via relative path) and React frontend components. It must NOT import from `convex/`, `@convex/`, or use any Convex-specific APIs.

Pure functions:

1. `adaptForTwitter(body: string, hashtags?: string[]): { text: string; isThread: boolean; tweetCount: number }` — Inline a simple thread splitter (do NOT import from `convex/twitter/threadSplitter` — that file lives in the Convex backend and cannot be imported client-side). Logic: If content <= 280 chars, return as single tweet. If longer, split at sentence boundaries into chunks of <=280 chars each. If hashtags provided and space allows, append top 3 as #tag at the end of first tweet. Return adapted text (or first tweet for preview), thread flag, and tweet count.

2. `adaptForLinkedIn(body: string): { text: string; truncated: boolean }` — LinkedIn max is 3000 chars. If body exceeds, truncate at last sentence boundary before 2990 chars and append "..." Return text and truncated flag.

3. `adaptForInstagram(body: string, hashtags?: string[]): { caption: string; hashtagsAdded: number; hashtagsList: string[] }` — Instagram max 2200 chars. The `hashtags` parameter receives values from `content.metadata.targetKeywords` (the existing Target Keywords field in the content table). If hashtags provided and not already in body, format each as `#keyword` (lowercased, spaces removed), append up to 30 at the end (separated by double newline from body). Truncate total to 2200 if needed. Return caption, count of hashtags added, and the formatted hashtagsList (for display in the preview UI).

4. `adaptContentForPlatforms(body: string, platforms: string[], hashtags?: string[]): Record<string, { adaptedText: string; metadata: Record<string, unknown> }>` — Calls the appropriate adapter for each platform in the array. Returns a map of platform -> adapted content with metadata.

Export types: `AdaptedContent`, `PlatformAdaptation`.

**Important:** This file is the SINGLE SOURCE OF TRUTH for adaptation logic. Both the Convex action (if it ever needs adaptation) and the React preview components import from here. No duplicated logic.

Create `convex/crossPlatform/actions.ts` with:

1. `publishToMultiplePlatforms` — A Convex action (NOT internalAction, user-facing) that:
   - Args: `contentId: v.id("content")`, `platforms: v.array(v.string())` where each string is "linkedin" | "twitter" | "instagram", `instagramImageUrl: v.optional(v.string())` (required if instagram is in platforms)
   - Auth: Use `getUserId(ctx)` from `../auth` helper (same pattern as other actions)
   - Validates content exists and is approved/scheduled
   - For each platform in the array, calls the corresponding platform action: `api.linkedin.actions.publishToLinkedIn`, `api.twitter.actions.publishToTwitter`, `api.instagram.actions.publishToInstagram`
   - Uses `Promise.allSettled` to run all platform publishes in parallel (one failure should not block others)
   - Returns `{ results: Array<{ platform: string; success: boolean; error?: string; url?: string }> }` with per-platform results
   - Important: Instagram publish requires imageUrl. If instagram is in platforms but no instagramImageUrl provided, return error for instagram platform only, still publish to others.
   - Twitter action needs contentId only (it reads content internally). LinkedIn needs contentId only. Instagram needs contentId + imageUrl + mediaType.
   - Do NOT adapt content here — each platform action already handles its own content. The adaptation is for PREVIEW purposes only (used by frontend Plan 16-02).

Spanish error messages consistent with existing patterns ("Error al publicar en {platform}", etc.).

Create `convex/crossPlatform/queries.ts` with authenticated queries:

1. `getUnifiedPublishHistory` — Convex query (user-facing, authenticated):
   - Args: `limit: v.optional(v.number())` (default 50)
   - Uses `getUserId(ctx)` for auth
   - Queries all 3 publish log tables: `linkedinPublishLog`, `twitterPublishLog`, `instagramPublishLog`
   - For each log entry, fetches the associated content title using `ctx.db.get(log.contentId)` (content table)
   - Normalizes into unified format: `{ _id: string, platform: "linkedin" | "twitter" | "instagram", contentId: Id<"content">, contentTitle: string, status: "pending" | "published" | "failed" | "deleted", publishedAt?: number, createdAt: number, error?: string, platformUrl?: string, metadata?: Record<string, unknown> }`
   - For LinkedIn: extract `linkedinPostUrn` into metadata, no direct URL
   - For Twitter: extract `tweetIds`, `isThread`, `threadUrl` into metadata. Use `tweetIds?.[0]` to construct URL if username known (from twitterConnections)
   - For Instagram: extract `instagramMediaId`, `mediaType`, `permalink` into metadata
   - Merges all entries, sorts by `createdAt` descending (newest first)
   - Applies limit
   - Returns array of unified entries

2. `getPublishingSummary` — Convex query (user-facing, authenticated):
   - No args
   - Counts: total published per platform, total failed, total pending
   - Returns `{ linkedin: { published: number, failed: number, pending: number }, twitter: { ... }, instagram: { ... }, total: { published: number, failed: number, pending: number } }`
   - Useful for the dashboard summary stats

Follow existing query patterns from `convex/linkedin/queries.ts` for auth and structure.
