# Architecture

**Analysis Date:** 2026-01-27

## Pattern Overview

**Overall:** Three-tier distributed architecture with agent-based orchestration

**Key Characteristics:**
- Real-time state management through Convex backend
- Client-side React UI with Next.js 16 (App Router)
- Multi-agent system with hierarchical organization and handoff patterns
- External orchestration via n8n workflows
- Direct Claude API integration for LLM execution
- Cron-based scheduling for automated task execution

## Layers

**Frontend (Next.js/React):**
- Purpose: User interface for dashboard, agent management, content review, and analytics
- Location: `ai-marketing-department/ai-marketing-department/app/`, `ai-marketing-department/ai-marketing-department/components/`
- Contains: Page components (app router), UI components, charts, layout shells
- Depends on: Convex React client, Lucide icons, Framer Motion, Recharts
- Used by: End users, dashboard consumers

**Convex Backend (Serverless Functions):**
- Purpose: Central data store, real-time queries/mutations, and agent orchestration actions
- Location: `convex/`
- Contains: Database schema (11 tables), queries, mutations, actions, cron jobs
- Depends on: Claude API, n8n webhooks, Anthropic SDK
- Used by: Frontend via Convex React client, n8n workflows via webhooks

**External Orchestration (n8n):**
- Purpose: Workflow automation, multi-step task coordination, webhook handling
- Location: `n8n-workflows/`
- Contains: Agent workflows, orchestration flows, task dispatcher
- Depends on: Convex API, Claude API indirectly via Convex
- Used by: Scheduled agents, manual triggers, webhook-based activations

## Data Flow

**Task Execution Flow:**

1. User/webhook creates task → `createTask` mutation stores in `tasks` table
2. Agent queries `getAgent` to fetch configuration
3. Agent executes via `executeAgent` action
   - Fetches system prompt from agent config
   - Calls Claude API with `callClaude` action
   - Records execution metrics in `executions` table
4. Agent generates content → stored in `content` table
5. Status changes trigger handoffs via `createHandoff` mutation
6. Handoff routes task to next agent in workflow
7. Final content status → `approved` or `published` via updateContentStatus

**State Management:**
- Convex holds single source of truth for all entities (agents, tasks, content, campaigns)
- Real-time updates via Convex subscriptions in React components
- No client-side state management library (Convex handles state)
- Optimistic updates possible through Convex mutations

**Cron Job Flow:**

1. Scheduled time triggers (hourly/daily/weekly) in `crons.ts`
2. Cron calls `runScheduledAgents` action with trigger type
3. Action fetches agents matching trigger from database
4. For each agent, executes workflow similar to task execution
5. Results recorded in `executions` and status tables

## Key Abstractions

**Agent:**
- Purpose: Represents a single AI personality in the marketing department
- Examples: `convex/schema.ts` (agents table), `convex/seed.ts` (agent definitions)
- Pattern: Each agent has agentId, systemPrompt, config, triggers, and optional reporting hierarchy
- 37 agents pre-defined across 7 departments with roles (cmo, director, specialist)

**Task:**
- Purpose: Unit of work assigned to an agent
- Examples: `convex/schema.ts` (tasks table)
- Pattern: Contains input, status lifecycle (pending → queued → running → completed/failed), retry logic, parent/child relationships
- Used for tracking work across handoffs and subtasks

**Handoff:**
- Purpose: Transfer of work between agents with context preservation
- Examples: `convex/functions.ts` (createHandoff mutation)
- Pattern: Contains source agent, destination agent, task reference, payload, status tracking (pending → accepted → completed)
- Enables hierarchical workflows where agents delegate to specialists or managers

**Content:**
- Purpose: Output artifacts (blog posts, tweets, emails, etc.) generated by agents
- Examples: `convex/schema.ts` (content table)
- Pattern: Rich metadata (SEO, hashtags, tone, target audience), status workflow (draft → review → approved → published), repurposing support
- Type variants: blog, social_linkedin, social_twitter, email, newsletter, ad_copy, landing_page, whitepaper, case_study, video_script

**Execution:**
- Purpose: Log of agent execution attempts with metrics
- Examples: `convex/schema.ts` (executions table)
- Pattern: Records tokens used, cost, duration, step-by-step execution log, success/failure status
- Drives analytics and cost tracking

**Campaign:**
- Purpose: Grouping of content and agents for coordinated marketing initiatives
- Examples: `convex/schema.ts` (campaigns table)
- Pattern: Links multiple content items, agents, budget tracking, goal metrics
- Type variants: content, paid, email, social, integrated

## Error Handling

**Strategy:** Two-tiered error handling with retry logic and escalation

**Patterns:**
- Task-level retries: `maxRetries` field in tasks table allows automatic re-execution (up to max attempts)
- Execution logging: Failed executions recorded in `executions` table with error message, code, stack
- Handoff escalation: If agent fails, handoff status → rejected, escalates to manager/CMO
- API errors: Claude API errors caught in `callClaude` action, wrapped with descriptive message
- Database failures: Convex mutations handle transactional consistency
- Error tracking: `error` field in tasks table and executions for debugging

## Cross-Cutting Concerns

**Logging:**
- Approach: Execution logs in `executions` table with step-by-step duration tracking
- No external logging service configured; database serves as audit trail
- Convex provides console output in dev mode

**Validation:**
- Approach: Schema validation via Convex `v` validators in all mutations/actions
- Enum validation for statuses, departments, roles, trigger types
- Type safety through TypeScript strict mode

**Authentication:**
- Approach: Currently not implemented; assumes trusted environment
- Claude API auth via ANTHROPIC_API_KEY environment variable
- Convex auth handled by deployment (CONVEX_DEPLOYMENT variable)

**Cost Tracking:**
- Approach: Token usage and cost calculated in `executions` table after Claude API calls
- `tokensUsed` object tracks input/output tokens, `cost` field stores estimated USD cost
- Metrics table can aggregate costs by period for billing insights

## Database Schema Overview

Core tables in `convex/schema.ts`:

| Table | Purpose | Key Fields |
|-------|---------|-----------|
| agents | Agent definitions | agentId, department, role, status, systemPrompt, triggers, reportsTo |
| tasks | Work units | taskId, agentId, status, input, output, retryCount, parentTaskId |
| executions | Execution logs | taskId, agentId, tokensUsed, cost, duration, status |
| handoffs | Agent transfers | fromAgent, toAgent, taskId, status, payload |
| content | Generated artifacts | contentId, type, status, createdBy, publishedUrl |
| campaigns | Marketing initiatives | campaignId, type, budget, goals, metrics, assignedAgents |
| keywords | SEO tracking | keyword, currentPosition, volume, difficulty, history |
| prompts | Prompt library | promptId, template, variables, category |
| metrics | Aggregated data | type, entityId, period, data |
| settings | System config | key, value |
| auditLog | Change history | action, entityType, performedBy, changes, timestamp |
